## 1. Сценарионууд

### Performance сценарио (`/cart/add`)
* **Тойм:** Хэрэглэгч сагсанд бараа нэмэх үеийн гүйцэтгэлийн хурдыг шалгах.
* **Системийн төлөв:** Сервер хэвийн асаалттай, ачаалалгүй.
* **Орчны төлөв:** Өөрийн компьютер (локал орчин, Linux/amd64, Node.js API).
* **Гадаад өдөөлт:** 20 виртуал хэрэглэгч (VU) 1 минутын турш сагсанд бараа нэмэх POST хүсэлт илгээнэ.
* **Шаардлагатай хариу:** Сервер алдаагүйгээр 200 OK буцааж, агшин зуур хариулах.
* **Хэмжүүр:** `/cart/add` хүсэлтийн p95 хариу өгөх хугацаа 200мс-ээс бага байх (`p(95) < 200ms`).

### Performance сценарио / Нэмэлт (`/report`)
* **Тойм:** Тайлангийн мэдээлэл татан авахад систем саатахгүй ажиллах эсэхийг хянах.
* **Системийн төлөв:** Сервер хэвийн ажиллаж байгаа, өгөгдөл бэлэн.
* **Орчны төлөв:** Локал орчин, 200-400мс санамсаргүй сааталтай endpoint.
* **Гадаад өдөөлт:** 20 VU нэгэн зэрэг `/report` GET хүсэлт илгээнэ.
* **Шаардлагатай хариу:** Зохих хугацаанд амжилттай 200 OK буцаах.
* **Хэмжүүр:** `/report` хүсэлтийн p95 хариу өгөх хугацаа 450мс-ээс бага байх (`p(95) < 450ms`).

### Reliability сценарио (`/pay`)
* **Тойм:** Төлбөр тооцоо хийх үеийн систем дэх эвдрэлийн давтамж, найдвартай байдлыг шалгах.
* **Системийн төлөв:** Сервер ажиллаж байгаа бөгөөд кодонд ~5%-ийн санамсаргүй алдаа (500 Gateway Timeout) тохируулсан.
* **Орчны төлөв:** Локал орчин.
* **Гадаад өдөөлт:** Хэрэглэгчид төлбөр төлөх POST хүсэлт дараалан илгээнэ.
* **Шаардлагатай хариу:** Төлбөрийн алдааны хувь хэмжээ зөвшөөрөгдөх хязгаарт байна.
* **Хэмжүүр:** `/pay` endpoint-ийн алдааны хувь (Error rate) 8%-аас бага байх (`rate < 0.08`).

### Availability сценарио (Сервер унаж, дахин асах)
* **Тойм:** Сервер гэнэт зогсоод буцаж асах үед систем тэсвэрлэх байдлыг турших.
* **Системийн төлөв:** Туршилт явагдаж байх үед сервер гэнэт унах (18 секунд зогсоно).
* **Орчны төлөв:** 1 минутын туршилтын хугацаанд, 20–43 дахь секундэд сервер унтарна.
* **Гадаад өдөөлт:** k6 ажиллаж байх үед серверийг `Ctrl+C`-ээр зогсоож, тодорхой хугацааны дараа дахин асаах.
* **Шаардлагатай хариу:** Сервер дахин асмагц систем хэвийн ажиллаж хүсэлтийг хүлээн авна.
* **Хэмжүүр:** Нийт хүсэлтийн амжилтын хувь (Availability) 90%-иас дээш байх (`checks rate > 0.90`).

## 2. SLO хүснэгт ба Error Budget тооцоо

| Сценарио | SLI (Юу хэмжих вэ) | Босго (Threshold) | Цонх / Нөхцөл |
| :--- | :--- | :--- | :--- |
| **Performance (Cart)** | `/cart/add` latency | `p(95) < 200 ms` | 20 VU, 1 мин |
| **Performance (Report)** | `/report` latency | `p(95) < 450 ms` | 20 VU, 1 мин |
| **Reliability** | `/pay` error rate | `rate < 0.08` (< 8%) | 20 VU, 1 мин |
| **Availability** | Амжилттай хүсэлтийн хувь (`checks`) | `rate > 0.90` (≥ 90%) | 1 мин, 18с зогсолт орсон |

* **Босго сонгосон үндэслэл:** Локал дээр `/cart/add` агшин зуур (~1-2мс) хариулдаг тул `p(95) < 200ms` нь бодит ачааллыг дааж байгааг батлах босго юм. `/report` дээр кодондоо 200-400мс сааталтай тул `p(95) < 450ms` гэсэн босго яг тохирно. `/pay` дээр 5% алдаа суулгасан тул магадлалын хазайлтыг тооцож `rate < 0.08` (8%) гэж сонгосон.
* **Error Budget тооцоо (Цагаар болон Хүсэлтээр):** 1 минутын (60 секунд) туршид 90% availability гэдэг нь **цагаар бодоход 6 секундийн зогсолт (downtime)** хийх зөвшөөрөгдөх budget юм. Туршилтаар серверийг ~18-20 секунд унтраасан тул ЦАГААР бодсон budget (6с) шууд хэтэрсэн.

## 3. k6 Тестийн үр дүн

### 3.1 Хэвийн үеийн тест (PASS)
Бүх threshold-ууд амжилттай **PASS** болсон (`exit=0`):
* **Availability (`checks` rate):** `98.74%` (2752/2787 амжилттай) -> `rate > 0.90` **✓**
* **`/cart/add` p95 latency:** `1.42 ms` -> `p(95) < 200ms` **✓**
* **`/report` p95 latency:** `391 ms` -> `p(95) < 450ms` **✓**
* **`/pay` error rate:** `3.76%` (35/929 алдаа) -> `rate < 0.08` **✓**

### 3.2 Chaos туршилт (Сервер унагаах)
Серверийг туршилтын явцад зориуд унтрааж ажиллуулсан бодит үр дүн:
* **Availability (`checks` rate):** **62.93%** (1922/3054) болж огцом буурсан -> `rate > 0.90` **✗ FAIL**
* **`/pay` error rate:** **39.29%** (400/1018) болж өссөн -> `rate < 0.08` **✗ FAIL**

**Цаг ба Хүсэлтийн Error Budget-ийн зөрүүний тайлбар:**
k6 нь metric болон check-үүдийг **ХҮСЭЛТИЙН тоогоор** тооцдог. Хэвийн үед `/report` зэрэг endpoint хариу иртлээ хүлээгддэг тул секундэд цөөн хүсэлт явдаг. Гэтэл сервер унасан хугацаанд хүсэлтүүд сааталгүйгээр агшин зуур (`connection refused`) буцаж байсан тул 1 секундэд хэвийн үеэс олон дахин олон хүсэлт эвдэрсэн байна. Иймээс нийт хүсэлтийн тоо нэмэгдэж (3054), алдааны хувь маш хурдан өсөж error budget-ийг шууд шатаасан.

### 3.3 Зориуд FAIL болгосон тест (`slo-test-fail.js`)
`/report`-ийн threshold-ийг `p(95)<100` болгож чангатган ажиллуулахад:
* **FAIL болсон үзүүлэлт:** `http_req_duration{name:report}` нь `p(95)=390.6ms` гарч `p(95)<100` босгыг давсан тул **✗ FAIL**.
* **EXIT CODE:** **`exit=99`**
k6 нь аль нэг threshold эвдэгдсэн тохиолдолд exit code `99` буцаадаг бөгөөд CI/CD пайплайн үүнийг таньж дараагийн шат руу нэвтрүүлэхгүй зогсоох боломжтой болдог.

## 4. Дүгнэлт

1. Энэхүү лабораторийн ажлаар чанарын сценарионоос SLO гаргаж, k6 threshold болгон кодчлох автоматжуулалтын бүрэн шугамыг тууллаа.
2. Сценарионоос SLO руу шилжихэд системд тохирсон бодит тоон босгыг хэмжилт дээр суурилж сонгох нь хамгийн чухал байв.
3. Локал орчинд `/cart/add` маш хурдан хариулдаг тул босгыг хэт сул тавих нь хэмжилтийг утгагүй болгодог гэдгийг ойлгосон.
4. Chaos инженерчлэлийн туршилт (серверийг 20–38 дахь секундэд зогсоох) нь системийн бэлэн байдлын бодит эвдрэлийг тодорхой харуулсан.
5. Сервер унасан үед хүсэлтүүд сааталгүйгээр агшин зуур буцдаг тул 18 секундийн зогсолт хүсэлтийн 31.63%-ийг унагаж, error budget-ийг маш хурдан шатаасан.
6. Туршилтаар дэд бүтцийн нэг уналт нь availability (68.36%) болон reliability (34.69%) хоёр SLO-г нэгэн зэрэг зөрчдөгийг баталлаа.
7. Иймд цаашид сүлжээний уналтыг бизнесийн логикийн алдаанаас тусгаарлаж хэмжих шаардлагатайг ойлгож авсан.
8. k6-ийн exit code (99) нь CI/CD пайплайн дээр чанарын шаардлага хангаагүй кодыг цааш гаргахгүй зогсоох гол механизм болдог.
9. Энэхүү туршилт нь программ хангамжийн чанарыг кодоор дамжуулан автоматаар хянах практик туршлагыг олгосон.
